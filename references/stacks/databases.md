## Local development
- `env_check.py` shows whether Docker or database servers exist on the machine.
- Without them, use one of:
  - SQLite (file-based, no install with `bun:sqlite`, `better-sqlite3` or libSQL);
  - a hosted dev database (a Supabase project, a Neon branch, a Turso database, Upstash);
  - installing Docker (ask the user first).
- Keep a seed script so any agent can recreate realistic data.
- The connection string lives in `.env.local` (ignored by git). `.env.example` lists the variable names with placeholder values.

## Schema and migrations
- Every schema change is a migration file in git, generated by the ORM or CLI (`drizzle-kit generate`, `prisma migrate dev`, `supabase migration new`). Never change a shared database by hand.
- Review generated SQL before applying it. A destructive step (drop, rename, type change) needs separate user approval and a backup.
- Follow expand → migrate data → contract for live systems (build.md).
- Regenerate types after each migration.

## ORM notes
- **Drizzle:** schema in TypeScript, SQL-like queries, and many drivers (node-postgres, postgres.js, Neon serverless, libSQL, bun:sqlite, MySQL). Check that the driver matches the runtime and host (edge needs HTTP/WebSocket drivers).
- **Prisma:** schema-first (`schema.prisma`), generated client, migrations, Studio. Check its install and generation step and its runtime support for the chosen host in the installed major's docs. `latest.py prisma` warns when a prerelease is tagged latest.
- Use a raw driver only for small scripts. Parameterize every query; never concatenate user input into SQL.

## Security and data handling
- Least privilege: the app connects with a role that can do only what it needs. Admin or service keys stay server-only.
- Postgres row-level security when clients query directly (Supabase). Server-side checks when an API sits in front.
- Indexes for the columns you filter and join on. Check slow queries with `EXPLAIN`.
- Personal data: store only what the brief needs. Note retention and the PDPA consent duties in the brief.
- Backups: know where they are (hosted provider settings or a dump script) before the first production deploy.

## Verify
Run the migrations on a fresh database, then the seed, then the app's data paths. Test as an anonymous user and as an authorized user, and confirm forbidden reads and writes fail.
